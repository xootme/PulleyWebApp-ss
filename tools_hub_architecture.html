Option Comparison

Two viable architectures exist. Both achieve the same URL structure (tools.cheapcadtools.com/pulleys, /gears, etc.). The routing problem Render cannot solve natively is handled by a Cloudflare Worker — which is free, unlimited, and entirely separate from the 3 Page Rule limit.
Cloudflare Workers ≠ Page Rules. Workers run on Cloudflare's edge network and have 100,000 free requests/day with no script limit. They are not affected by the 3-rule cap.
Criteria Option C — Independent Services + Worker Option D — Monorepo / Flask Blueprints
URL structure tools.cheapcadtools.com/pulleys ✓ tools.cheapcadtools.com/pulleys ✓
Existing app refactor None — PulleyWebApp works as-is Yes — convert to Flask Blueprint
Adding a new tool Fully automated via GitHub Action Manual — edit app.py + registry.json
Tool isolation Full — tools fail independently None — one crash affects all tools
Independent deploys Yes — push to any tool repo No — all tools redeploy together

Render free-tier services 1 per tool (hub + N tools) 1 total
Best for 5+ tools, multiple contributors, long-term growth 2–3 tools, solo developer, fast start
Recommendation: Option C. The existing PulleyWebApp requires no changes, deployment of every future tool is fully automated, and tools are isolated from each other. The Cloudflare Worker is ~15 lines of code and costs nothing.

1

Cloudflare Worker — Path Routing

A single Cloudflare Worker sits in front of all Render services and routes requests by path. It is deployed once to tools.cheapcadtools.com and updated whenever a new tool is added. It runs on Cloudflare's global edge — zero latency overhead, zero cost on the free tier.
worker.js
export default {
  async fetch(request) {
    const url = new URL(request.url);
    const path = url.pathname;

    // Route each tool path to its Render service
    if (path.startsWith('/pulleys'))
      return fetch('https://pulleywebapp.onrender.com' + path, request);

    if (path.startsWith('/gears'))
      return fetch('https://gearapp.onrender.com' + path, request);

    // Default: hub selector
    return fetch('https://tools-hub.onrender.com' + path, request);
  }
}
Adding a new tool = adding one if block and redeploying the Worker. This can itself be automated by the GitHub Action (Step 3).

Standardised Tool Repo Structure

Every tool repo follows the same layout. The critical file is tool.json — it is what the hub reads to build the selector page, and what the GitHub Action reads to know what to name the Render service.
Directory layout
my-new-tool/
├── app.py              # Flask app — must have @app.route('/')
├── requirements.txt
├── tool.json           # metadata read by hub and GitHub Action
├── Procfile            # web: gunicorn app:app
└── .github/
    └── workflows/
        └── deploy.yml  # copy from template — no edits needed
tool.json
{
  "name":        "Timing Pulley Generator",
  "slug":        "pulleys",
  "description": "SVG, DXF, and STEP exports for timing belt pulleys",
  "icon":        "⚙",
  "url":         "https://tools.cheapcadtools.com/pulleys",
  "status":      "live"
}
The slug becomes the Render service name and the URL path. Keep it short, lowercase, no spaces. The PulleyWebApp only needs this file added — nothing else changes.

GitHub Action — Auto-Provision on Push

Each tool repo contains a workflow at .github/workflows/deploy.yml. When code is pushed to main, the action creates (or redeploys) the Render service and notifies the hub registry to update.
.github/workflows/deploy.yml
name: Deploy to Render

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Read slug from tool.json
        id: meta
        run: echo "slug=$(jq -r .slug tool.json)" >> $GITHUB_OUTPUT

      - name: Create or redeploy Render service
        run: |
          curl -sf -X POST https://api.render.com/v1/services \
            -H "Authorization: Bearer ${{ "{{" }} secrets.RENDER_API_KEY {{ "}}" }}" \
            -H "Content-Type: application/json" \
            -d '{
              "name":         "${{ "{{" }} steps.meta.outputs.slug {{ "}}" }}",
              "type":         "web_service",
              "repo":         "${{ "{{" }} github.repository {{ "}}" }}",
              "branch":       "main",
              "buildCommand": "pip install -r requirements.txt",
              "startCommand": "gunicorn app:app",
              "plan":         "free"
            }'

      - name: Notify hub to refresh registry
        run: |
          curl -sf -X POST \
            https://api.github.com/repos/xootme/tools-hub/dispatches \
            -H "Authorization: Bearer ${{ "{{" }} secrets.HUB_DISPATCH_TOKEN {{ "}}" }}" \
            -H "Accept: application/vnd.github.v3+json" \
            -d '{"event_type":"tool-registered",
                 "client_payload":{"slug":"${{ "{{" }} steps.meta.outputs.slug {{ "}}" }}"}}'
RENDER_API_KEY and HUB_DISPATCH_TOKEN are stored as GitHub repository secrets — never in code.

Hub Registry — registry.json

The tools-hub repo maintains a registry.json listing every live tool. When a tool repo fires the tool-registered dispatch event, a second Action in tools-hub fetches that tool's tool.json, merges it into registry.json, and pushes — which triggers a Render redeploy of the hub.
registry.json
[
  {
    "name":        "Timing Pulley Generator",
    "slug":        "pulleys",
    "description": "SVG, DXF, and STEP exports for timing belt pulleys",
    "icon":        "⚙",
    "url":         "https://tools.cheapcadtools.com/pulleys",
    "status":      "live"
  },
  {
    "name":        "Gear Generator",
    "slug":        "gears",
    "description": "Involute spur and helical gear profiles for CAD",
    "icon":        "🔩",
    "url":         "https://tools.cheapcadtools.com/gears",
    "status":      "coming_soon"
  }
]
tools-hub/.github/workflows/update-registry.yml
on:
  repository_dispatch:
    types: [tool-registered]

jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Fetch tool.json from source repo
        run: |
          SLUG="${{ "{{" }} github.event.client_payload.slug {{ "}}" }}"
          curl -sf https://raw.githubusercontent.com/xootme/${SLUG}/main/tool.json \
            -o /tmp/tool.json

      - name: Merge into registry.json
        run: python scripts/update_registry.py /tmp/tool.json registry.json

      - name: Commit and push
        run: |
          git config user.email "actions@github.com"
          git config user.name  "GitHub Actions"
          git add registry.json
          git commit -m "Register tool: ${{ "{{" }} github.event.client_payload.slug {{ "}}" }}"
          git push

Hub App — Flask Selector Page

tools-hub/app.py
import json
from flask import Flask, render_template

app = Flask(__name__)

def load_registry():
    with open('registry.json') as f:
        return json.load(f)

@app.route('/')
def hub():
    tools = load_registry()
    return render_template('hub.html', tools=tools)
templates/hub.html (simplified)
<!-- One card per tool, built from registry.json -->
{% for tool in tools %}
  <div class="tool-card">
    <div class="tool-icon">{{ tool.icon }}</div>
    <div class="tool-name">{{ tool.name }}</div>
    <div class="tool-desc">{{ tool.description }}</div>
    {% if tool.status == 'live' %}
      <a href="{{ tool.url }}" class="btn-launch">Open →</a>
    {% else %}
      <span class="btn-soon">Coming Soon</span>
    {% endif %}
  </div>
{% endfor %}
Tools with "status": "coming_soon" appear as greyed-out teaser cards — useful for announcing tools before they are ready.

Adding a New Tool — End-to-End

After one-time setup, adding a tool is 4 steps:
1 — Create the repo from the template
cookiecutter gh:xootme/.github --directory=tool-template
# Prompts for: name, slug, description, icon
# Generates: app.py stub, requirements.txt, tool.json, deploy.yml
2 — Write the tool
Build the Flask app. Only requirement: @app.route('/') returns the tool's main UI.
3 — Add a path entry to the Cloudflare Worker
if (path.startsWith('/new-tool-slug'))
  return fetch('https://new-tool.onrender.com' + path, request);
4 — Push to GitHub
git add .
git commit -m "Initial release"
git push origin main
This single push triggers everything — Render provisioning, registry update, and hub redeploy are all automatic. Within ~3 minutes the tool is live and the hub card appears.

Updating an Existing Tool

No extra steps — push to main as normal. The deploy.yml Action redeploys only that tool's Render service. All other tools stay up and unaffected. 
git add .
git commit -m "Update: describe change"
git push origin main
# Only this tool's Render service redeploys — live in ~2 minutes
